# 004. 計測が静かに壊れる — プールの個体をスロット番号で数えてはいけない

実装の失敗ではなく、**検証の失敗**の話。実装は正しかったのに「動いていない」と誤読しかけた。
自動テストが緑でも、測り方が間違っていれば結論は嘘になる。

## 何を作ろうとしたか

敵16種のうち、まずステージ1に出る5種
(スキャッター/ドリフター/リーパー/ガンワゴン/ホイールソー)を実装したところだった。

このゲームは**エンティティをプールで持つ**。`ENEMIES` は固定長20の配列で、
敵が出るときは空きスロットを1つ取って `alive = true` にし、画面外へ出たら `alive = false` に戻す。
毎フレーム `new` しないための普通の作りで、DMG移植性ルール(frame内で割り当て禁止)からも必須だった。

検証は Node から直接ゲームを回して、フレームごとにプールを走査する形で書いていた。
ブラウザを使わないので速く、決定論的で、同じシードなら毎回同じ数字が出る。

## こちら側の指示(原文)

> 各グループごとに動作を実測してから次へ進むこと。全部書いてから検証しない。

> 報告に必ず含める数値:
> - 5種すべてが実際に出現すること(種類ごとの出現ウェーブ数)
> - **ガンワゴンが画面上部に留まる**こと(y座標の範囲)と、**退場して消える**こと(生存フレーム数の上限)
> - **ホイールソーが左右端で跳ね返る**こと(x座標の反転回数と範囲)、**自弾で壊れない**こと

指示は妥当だった。問題はこちらの測り方にあった。

## 何が起きたか

ガンワゴンとホイールソーの挙動を測ろうとして、こういうプローブを書いた。

```js
const track = new Map();          // key: スロット番号
ent.forEach(ent.ENEMIES, (e, idx) => {
  if (!track.has(idx)) track.set(idx, { kind: e.kind, fire: 0, frames: 0 });
  const t = track.get(idx);
  t.frames++;
  t.fire = Math.max(t.fire, e.fireCount);
});
```

4000フレーム回して出てきた結果はこうだった。

```
個体0 kind=0 発射=0 ...
個体1 kind=1 発射=1 ...
個体2 kind=1 発射=1 ...
```

`kind=3`(ガンワゴン)も `kind=4`(ホイールソー)も**1体も出ていない**ように見えた。
最初は「ウェーブが後半まで進んでいないのだろう」と考え、次に「スポーンが止まっているのでは」と疑った。

さらに前段では、別のプローブで「30000フレーム回してもウェーブが3つしか出ない」という数字も出ていた。
これも一瞬「ウェーブ制が壊れている」と読みかけた。

## なぜそうなったか

**原因は2つあり、どちらも実装ではなく計測側にあった。**

### 1. スロット番号は個体の identity ではない

プールのスロットは使い回される。スロット3に居た敵が画面外へ出て消え、
30フレーム後に別のウェーブの別の種類の敵が同じスロット3に入る。

スロット番号をキーにすると、この2体は**同じ個体として1つのレコードにまとまる**。
`kind` は最初に書き込んだ値のまま残り、あとから入ってきたガンワゴンの kind=3 は上書きされない。
「ガンワゴンが1体も出ていない」のではなく、**出ていたのに古い個体のレコードに埋もれて見えなくなっていた**。

もっと悪いのは、これが**エラーにならない**ことだ。例外も出ず、テストも緑のまま、
数字だけがもっともらしい顔で嘘をつく。

### 2. オブジェクト参照を Set に入れても同じ

「ならオブジェクトそのものを Set に入れて数えれば別個体を区別できる」と考えたが、これも間違いだった。
プールは**同じオブジェクトを使い回す**(そうしないと毎フレーム割り当てが発生する)。
スロットが再利用されても参照は同じなので、`seen.has(e)` は true のままになり、
新しい個体を「もう見た」として取りこぼす。

### 3. おまけ: 「止まっている」ように見えたのは、ただの GAME OVER だった

30000フレームでウェーブが3つしか出なかった件は、切り分けたら
**プローブの自機が被弾死してゲームオーバーになっていた**だけだった(フレーム934で死亡)。
自動プレイのプローブは操作が下手なので普通に死ぬ。死ねばスポーンも止まる。当たり前だった。

## どう直したか

**個体の同一性を、値でできたキーで表す。** このゲームには既にウェーブ単位の連番
(`formationId`)があったので、それとスロット番号を組み合わせた。

```js
const key = e.formationId + ':' + idx;
```

同じスロットでも、別のウェーブの敵なら別のキーになる。これで
ガンワゴンは「発射3回/3回/2回で離脱、y=-16..24pxに居座る」、
ホイールソーは「自弾を撃ち続けても hp 1→1 で壊れない、左右で反転して降りる」と、
そのまま仕様どおりの数字が出た。実装は最初から正しかった。

ゲームオーバーの件は、**検証用の入口**を作って解決した。
`?wave=6&invuln=1` のように開始ウェーブと無敵を指定できるようにして、
測りたい敵のところから直接始める。URLの解釈は単体版のエントリからしか読まれない
モジュールに閉じてあるので、出荷物には入らない(grepで0件を実測)。

### 捨てた案

- **プローブを上手にプレイさせる**: 死なないように動かすのは本質的でないうえ、
  敵が増えるほど無理になる。無敵オプションのほうが安上がりで確実
- **スロットを使い回さない**: 毎フレームの割り当てを禁じている以上、選べない
- **個体に固有IDを振る**: 悪くないが、ゲーム側に検証専用のフィールドを増やすことになる。
  既にある `formationId` で足りるなら、そちらを使うほうが軽い

## 数字

| | 誤った計測 | 正しい計測 |
|---|---|---|
| ガンワゴンの観測数 | **0体**(出ていないと読んだ) | 3体。発射3/3/2回で離脱 |
| ホイールソーの観測数 | **0体** | 3体。hp 1→1(破壊不能)、左右反転あり |
| 4000フレームでの観測ウェーブ数 | 3(スポーンが止まったと読んだ) | 実際は GAME OVER(フレーム934)後の停止 |
| リーパーの生存フレーム | — | 63〜87(他種は450〜640。滞在が短いという設計どおり) |

もう1件、同じ日に踏んだ類似の罠がある。サンドワームの「浮上後に放射3発」を
`fireCount` で数えたら 0 のままで、未実装かと思った。実際は共通の発射パイプラインを通さず
直接撃つ実装だったので、カウンタが増えないだけだった。
フレームごとの**敵弾の増分**を見たら、浮上したフレームちょうどに +3 が立っていた。

## 一般化できること

- **プールを持つ設計では、スロット番号も参照も identity ではない。**
  「いつ入ったか」を含む値(世代番号・ウェーブID・スポーン連番)と組み合わせて初めて個体を指せる。
  再利用のある構造を数えるときは、まずキーの設計を疑う
- **計測の失敗は例外を出さない。** 実装のバグは落ちるか赤くなるが、
  計測のバグは「それらしい数字」を返す。**まず「出ていないはずのものが出ていない」ことを確かめる前に、
  「出ているはずのものが出ている」ことを確かめる**(今回なら、先に短時間で kind を全部並べれば10秒で気づけた)
- **観測系の状態をまず疑う。** 「止まっている」ように見えたら、対象ではなく観測している側
  (プローブが死んでいないか、状態遷移していないか)を先に見る
- **カウンタは「共通の経路を通ったもの」しか数えない。** 直接呼び出す実装が1つでもあると、
  カウンタ基準の検証は静かに漏れる。**結果側(実際に生成された弾の数)で測るほうが騙されにくい**
- 検証のために**開始位置と無敵を指定できる入口**を作るのは、ほぼ常に安い。
  1回作れば以降のすべての検証で効く。出荷物に入れない切り分けさえしておけばよい
