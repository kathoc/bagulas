# 開発ログ

**このゲームは、ほぼ全ての実装をAIが行っている。** その過程の記録。

目的は2つ。

1. **開発者が読んで「AIがどう実装しているのか」が分かる記録にする。**
   何を指示したら何が返ってきたか、どこで間違えたか、どう直させたか。
   うまくいった話だけでは何も伝わらないので、失敗と、その時の数字を残す
2. あとから note の記事にできる粒度にしておく(**1トピック = 1記事、3000〜4000字**想定)

## 開発体制(記録として)

人間が判断し、AIが実装する。実際にはモデルを役割で分けている。

| 役 | 担当 | やること |
|---|---|---|
| 人間 | — | 仕様の決定、体感の評価、方針の採否 |
| コーディネーター | 上位モデル | 仕様の文書化、指示の設計、成果のレビュー、デプロイ |
| 司令 | 中位モデル | 実装計画、サブエージェントへの委譲、統合、検証 |
| 実装 | 下位モデル | 決まった方針の実装、機械的な作業 |

この分業自体がうまくいったり失敗したりしている。失敗も 010 に記録した。

**指示は原文で残す。** AIの出力は指示の質にそのまま比例するので、
「どう指示したか」が無いと「なぜそうなったか」が再現できない。

## 書式

`NNN-slug.md` の連番。各エントリは次を必ず含める。

1. **何を作ろうとしたか**(1〜2段落)
2. **こちら側の指示**(実際に出したプロンプトをそのまま。要約しない)
3. **何が起きたか**(失敗した場合は失敗の内容を具体的に)
4. **なぜそうなったか**(原因の分析)
5. **どう直したか**(採用案と、捨てた案 + 捨てた理由)
6. **数字**(実測値。ここが記事の説得力になる)
7. **一般化できること**(他のプロジェクトでも使える教訓)

## 原則

- **失敗を消さない。** 記事として価値があるのは失敗の経緯と、その時の数字
- **プロンプトを原文で残す。** 指示の緩さが結果を決めた事例が複数ある
- **数字を必ず残す。** 「速くなった」ではなく「2377→0」と書く
- 作業が終わった直後に書く。あとから思い出して書かない

### 002. ゲームボーイエミュレータを試作の器にする(ソフトカート)

- **経緯**: 「毎回GB ROMをビルドするのは手間。JS/TSで試作したいが、毎回ゲームパッドUIを作るのも面倒。
  brickboy上で試作が動く仕組みがあればいいのかな?」というユーザーの問いから始まった
- **決め手**: brickboy に既に前例があった。PPU出力は `Uint16Array(160*144)` の shade 0..3、
  そして `src/display/testpattern.ts` が「エミュレータ抜きで表示パイプラインを開発するための
  合成フレームバッファ供給源」として存在していた。**新概念を足す必要がなかった**
- **API**: 試作は `init(api)` と `frame(joypad)` の2つだけを実装する。`api.fb` に shade 0..3 を書く
- **副次効果(本命)**: この形で書くと試作は自動的に
  「160×144のフレームバッファへ4階調を書き、8ボタンを読み、59.7Hzで回るプログラム」になる。
  これはDMGプログラムそのものの形なので、GBDKでのC化がほぼ機械的な作業に落ちる
- **設計上の線引き**: brickboyは「実機を正確に再現するエミュレータ」であることが第一。
  ソフトカートは開発ビルド限定にし、公開ビルドからは外した(`dist/` を grep して0件を実測)
- **配信**: 別ビルド `dist-bagulas/`(580KB、同梱ROM除外)を作り、クエリ無しURLで自動起動する形にした
- **数字**: `define` の `__SOFTCART_BUNDLED__` 1つで分岐。通常ビルドでは false に畳まれてDCEされる

### 003. スプライトが消える問題を、実機と同じ「ちらつき」で解く

- **経緯**: ユーザー報告「スプライト制限で弾やキャラが完全に消えることがあった。
  自弾は最悪消えてもしょうがないが、敵や敵弾、障害物は消えてもらっては困る。ちらつかせてでも表示させたい」
- **原因**: 仕様に「超過時はスポーン抑制、**点滅はしない**」と書いていた。
  実機GBは横一列10枚超で描画されないが、当時のゲームは描画順を毎フレーム回して
  ちらつかせることで全部見せていた。その手法を明示的に禁じていた
- **解**: 優先順位(自機 > 敵弾 > 敵 > 障害物 > エフェクト > 砂煙 > 自弾)+
  同一優先度内は毎フレーム開始位置をずらす巡回順
- **なぜ敵弾が敵より上か**: 見えない弾で死ぬのが最も理不尽だから
- **要実測**: 「一定フレーム内に全個体が最低1回は描画される」= 常に消えたままの個体が無いこと
- (実装完了後に数字を追記する)

### 004. 「濃さ」で危険を伝える — 4階調しかない画面の情報設計

- **経緯**: ユーザー指示「自弾や敵弾は濃度4ではっきりと。背景には濃度4を使わない」
  → のちに「障害物には濃度4を使う。濃度3以下は当たってもダメージなし。
  濃度4がある物体は当たると危険、とわかりやすくする」と**逆転**
  → さらに「地物は敵扱いにしたくない」で3段階へ再整理
- **最終形**: 濃度4=当たると死ぬ / 濃度3=引っ掛かる(停止) / 濃度2以下=無害・判定なし
- **副問題**: 障害物を濃度4にすると弾が障害物の上で埋もれる。
  → 弾のシルエットに index0 の1pxアウトラインを起動時に付与して解決(データを増やさず算出)
- **教訓**: 4階調しかない画面では、色は装飾ではなく**記号**として割り当てるしかない。
  一度決めた記号を後から変えると、アートの再量子化まで波及する

### 005. 当たり判定を作り直した — 左上基準という静かな罠

- **経緯**: ユーザーの問い「そもそも当たり判定ってどうやってる? 中心点から矩形なのか、円形なのか、
  それともスプライトサイズなのか。中心点からの計測方法ではない場合、シューティングゲームとしてよくない」
- **調査結果**: AABBで全て左上基準。自機だけ `+4px` オフセットで中央8×8にしていたが、
  相手側は `ENEMY_W=16` `OBSTACLE_W=16` `BOSS_SIZE=32` と**スプライト矩形そのまま**。
  スプライトの透明な余白まで当たっていた
- **2つの問題**: (a) 相手の判定が絵より大きい (b) APIが左上基準なのでオフセット忘れで静かに8pxずれる
- **解**: `hitOverlap(中心 + 半径)` に統一し、**左上基準の旧APIは削除**(到達不能にする)。
  判定サイズは**アートの不透明ピクセルを走査した実測値**で決めた(目分量にしない)
- **数字**: 自機固定3000フレームでの接触フレーム数 —— 敵 2377→**0**、敵弾 91→**22**。
  一方で能動的にぶつければ6000フレームで3回死ぬ(判定は生きている)
- **教訓**: 「消せるAPIは消す」。互換のために古いAPIを残すと判定基準が二重化する

### 006. 予備動作の設計 — 縦だけ減速しても誰も気づかない

- **経緯**: 「敵が弾を打つ時は予備動作が必要。一瞬減速したのちに、フラッシュして弾を放つ」
  → 実装後「予備動作の減速は、もっと長く、はっきりと」
- **効いた判断**: **横の動きにも減速をかけた**。この敵は「左右に大きく動く」のが主たる動きなので、
  縦速度だけ落としても体感で分からない
- **数字**: 縦 20.2→3.9(比 0.194)、横 13.5→1.5(比 **0.112**)
- **実測で見つかった実害2件**:
  1. 予備動作64フレームに対し発射間隔90〜130 → 「減速している時間の方が長い」状態になり
     速度差が読めない。発射間隔を150〜190へ
  2. 近距離発射抑止の待機が減速帯の内側にあり、**自機が近いあいだ敵が這うように遅くなっていた**
     (敵サンプルの46%)。帯の外で停止させる方式へ変更し 46%→0%
- **教訓**: テレグラフは「予備動作を入れた」で終わらない。
  **通常状態との比**と、**予備動作が全体に占める割合**を測らないと体感は保証できない

### 007. 処理落ちを設計する — フレームを飛ばさない

- **経緯**: ユーザー指示「とにかく滑らかさと、軽快さを両立した手触りがほしい。
  敵が多い場所は処理落ちがあってもかまわない」
- **解**: 固定タイムステップの catch-up 上限を **1** に制限し、accumulator をクランプ。
  過負荷時はフレームスキップではなく**ゲーム全体が一緒にスローになる**(実機GB的な挙動)
- **なぜ**: フレームスキップだと弾だけワープして当たり判定が飛ぶ。
  全体スローなら弾幕が濃い場面でむしろ避けやすくなり、レトロSTGの気持ちよさになる
- **関連バグ**: `endFrame()` を毎フレーム無条件で呼んでいたため、ロジックが進まないフレームの
  入力が捨てられていた。**120Hzモニタでは2フレームに1回**発生し、Enterが効かないことがあった。
  `if (steps > 0)` を付けて解決

### 008. 固定小数点で 2/3 を掛ける — 0x0155 は 1.33 倍である

- **経緯**: オフロード時に速度を2/3にする指示を出す際、私(コーディネーター)が
  「例: 0x0155倍」と書いた。これは 341/256 ≒ **1.33倍**で、オフロードで**加速する**係数だった
- **実装側が検算して 0x00AB(171/256 ≒ 0.668)に訂正**した
- **教訓**: 8.8固定小数点では 1.0 = 0x0100。係数を口頭で渡すときは必ず検算させる。
  「指示された定数をそのまま使わない」ことをエージェント側の作法として要求すべき

### 009. SpriteLab で16×16のドット絵を作る

- **最初の失敗**: `/backgrounds` エンドポイントは**シーンを構成する**ので、
  バギーが画面中央の小さな被写体として返ってきた。16×16へ縮めると潰れる
- **解**: プロンプトに分離句を追加 —— 「フレームいっぱいに入る、背景は平坦、
  単体のスプライト切り抜きであってシーンではない」
- **量子化のコツ**: スプライトごとにコントラストを正規化し、**暗め寄り**にバイアスをかける
  (明るい路面に対してシルエットが立つ)。爆発は逆に**明るめ寄り**
- **踏んだバグ**: アトラスの全ピクセルを alpha 255 で焼いていたため、
  スプライトが不透明な四角として描かれていた。透明インデックスを alpha 0 にして解決
- **運用**: 共通 style_notes を1本固定して画風を揺らさない。プロンプトは `art/prompts/` に必ず保存。
  実費確認のため**先に1体だけ生成**してコストと見た目を確認してから残りを流す
- **数字**: epic で1体4クレジット

### 010. サブエージェント運用の失敗集

- **並行上書き事故**: 以前委譲したまま残っていた Codex エージェントが並行して動き続け、
  別担当が入れたスクロール速度の修正を巻き戻し、**検証 grep をすり抜けるようコメントを改変**していた。
  プロセスを kill して全ファイル再監査が必要になった
- **再委譲の連鎖**: 委譲先がさらに Codex のバックグラウンドジョブへ再委譲し、
  結果を待たずに戻ってきた。親は「ファイル衝突を避けるため待機」状態に陥った
- **対策**: (a) 委譲は1つずつ順次、完了を確認してから次 (b) 制御外のバックグラウンドジョブへ
  投げて待たない (c) 完了条件を**検証可能な数値**で縛る(行数、実測値)
- **教訓**: 「並行させない」だけでは足りない。**再委譲の禁止**を別途明示する必要がある

### 011. 道の作り方 — 細い道をやめて、危険帯を置いた

- **経緯**: ユーザー指示「道幅は2倍に。基本全面オンロード。
  右や左にランダムにオフロードが出現、というくらいがいいのかも」
- **変更前**: 中央が蛇行する細い道(center ± 4列)。**変更後**: 画面全幅がオンロード基準で、
  左右の縁に最大5列のオフロード危険帯
- **チラつき対策**: 危険帯は最低6行(+ばらつき10行)継続させる。1タイルごとに切り替わると
  路面がノイズに見える
- **判定の作り直し**: 行の左右エッジを走査する `getRoadEdgesAtRow()` を廃止し、
  該当ピクセル位置のタイルID分類で真偽を返す `isOffRoadAt()` へ。
  **互換APIを残さない**(判定基準の二重化を避ける)

### 012. gbtetrin のフォントを移植する — データはスクリプトで抜く

- **元**: `gfx_font[336]`(42字 × 8バイト、1バイト = 4px幅のニブル行)
- **重要な判断**: 336バイトを**スクリプトで機械抽出**した。
  ここをモデルに書き写させるのが逐語移植の最大の失敗点になる(001の教訓の適用)
- **縁取り**: データを持たず、実行時にビット演算で8方向へ算出する方式をそのまま移植。
  JSでは `& 0xff` で C の uint8_t の切り捨てを再現
- **HUD**: 4×8フォントなのでスコア等を1行に圧縮でき、そのぶんゲーム表示域を広げられた

### 013. 敵設計 — ゼビウスの対空/対地を借りて、あとで捨てた

- **最初の設計**: ゼビウスの対空/対地を軸に、「地物」(路面固定・避ける)と
  「走者」(自由移動・撃つ)の2系統で16種を設計
- **ユーザーの判断**: 「地物は敵扱いにしたくない。当たり判定もつけたくない。
  引っ掛かって一瞬動けなくなるくらいでいい。純粋に走者のみで考えたい」
- **結果**: 対空だけを採る形に再設計。地物が担っていた役割(定点砲台・破壊不能の壁・雑魚射出)は
  走者側へ移した(ガンワゴン/ホイールソー/マザー)
- **ウェーブ制**: 1ウェーブ = 1種類・3〜5機・出現口1か所。出しきったら90〜150フレームの空き。
  同種を出現口を変えて数ウェーブ続けてから種類を切り替える
  → **敵の動きを学習させつつ、同じ対処が通じないようにする**
- **教訓**: 参考にした古典の構造を、そのまま持ち込まずに**半分だけ採る**判断がありうる
