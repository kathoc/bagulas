# 開発ログ

**このゲームは、ほぼ全ての実装をAIが行っている。** その作業記録。

## ここに何を残すか

`LOG.md` に **事実だけを時系列で追記**する。感想・評価・自己批評は書かない。
note の記事はあとから LOG.md を材料に清書するので、ここでは**素材の保存**に徹する。

## 追記はスクリプトで行う

```
node tools/devlog_sync.mjs        # 未記録のコミットを LOG.md へ追記
node tools/devlog_sync.mjs --dry  # 追記内容の確認だけ
```

git のコミット日時・ハッシュ・メッセージ本文をそのまま流し込む。
LOG.md に既に載っている最後のコミット以降だけを追記するので、何度実行しても重複しない。

したがって**コミットメッセージが一次記録**になる。
本文に「指示」「実装」「修正」「数値」を書いておけば、そのまま LOG.md に載る。

## 記録の形式(LOG.md)

1エントリ = 1コミット。上が古く、下が新しい。追記のみ。

```
## MM-DD HH:MM — 見出し(何をしたか、一行)

**指示**: ユーザー/コーディネーターが出した指示。原文のまま。要約しない
**判断**: AIが自分で決めたこと。採った案と、捨てた案
**実装**: 何を変えたか。ファイル名と要点
**修正**: 途中で直した不具合。原因と対処
**失敗**: 却下されたもの、やり直したもの、計測を誤ったもの
**数値**: 実測値。変更前→変更後
**コミット**: ハッシュ(スクリプトが自動で付ける)
```

- **タイムスタンプとコミットIDは必須**。あとでその時点の状態を再現して
  スクリーンショットを撮るために使う(`git checkout <hash>` で戻せること)
  - 日時は `MM-DD HH:MM`。年をまたぐ場合は `YYYY-MM-DD HH:MM`
  - コミットが複数なら全部並べる。コミットしていない作業も時刻付きで残す
- 書かない項目は省略してよい(空の見出しを並べない)
- **数値は必ず入れる**。「速くなった」ではなく「39 → 70」
- **AIが自分で決めた判断は必ず残す**。何を採り、何を捨てたか。
  人間の指示だけでは、あとから見て「なぜそうなったか」が再現できない
- **やったことは全部残す。失敗も含める。** 却下された実装、やり直し、
  計測の誤り、踏んだバグ。うまくいった結果だけでは記録の意味がない
- デプロイしたらURLと時刻を残す
- 1エントリは長くても20行程度

## 開発体制

| 役 | 担当 |
|---|---|
| 人間 | 仕様の決定、体感の評価、方針の採否 |
| コーディネーター | 上位モデル。仕様の文書化、指示の設計、レビュー、デプロイ |
| 司令 | 中位モデル。実装計画、委譲、統合、検証 |
| 実装 | 下位モデル。決まった方針の実装 |

## 旧形式について

`001-*.md` 〜 `005-*.md` は、この方針に切り替える前に記事形式で書いたもの。
内容は残すが、以降は追記しない。新しい記録はすべて `LOG.md` へ。

| # | 題 |
|---|---|
| 001 | 「移植して」と指示すると再実装される(原典1675行 → 生成物470行) |
| 003 | スプライト超過をちらつきで解く |
| 004 | プールの個体をスロット番号で数えると計測が壊れる |
| 005 | 仕様の曖昧さが実装と検証の両方を誤らせた |
