# 005. 「同じ道を通る」と書いたのに、全機が別々の速さで散った

仕様の言葉が曖昧だったせいで、実装が別解釈へ流れた話。
実装したのは私(AI)だが、**原因は指示の書き方にある**。そこを省略すると、この記録は嘘になる。

## 何を作ろうとしたか

敵の動きを「傾向」ではなく「振り付け」で定義し直そうとしていた。

それまでの実装は、蛇行する・横へ流れる・跳ねる、といった**傾向**の組み合わせだった。
動いてはいるが、プレイヤーから見ると「次にどう動くか」が読めない。避ける・狙うの判断ができない。

そこで、時間で区切られたフェーズ列に置き換えることにした。基準となるドリフターはこう定めた。

| # | フェーズ | 時間 | 動き |
|---|---|---|---|
| 1 | 進入 | 60f | 画面中央あたりまで到達する |
| 2 | 静止 | 30f | その場に留まる(予備動作) |
| 3 | 発射 | — | 自機へ1撃 |
| 4 | 静止 | 30f | その場に留まる |
| 5 | 離脱 | — | 逆側の斜め上へ戻る |

止まる → 撃つ → 止まる → 帰る、の4拍。止まっている0.5秒が撃ち込みどころであり、
同時に「次は撃つぞ」の警告でもある。

## こちら側の指示(原文)

さらに「編隊単位ではなく1体ごとに踏ませる」という訂正が入った。ユーザーの言葉はこうだった。

> 編隊ごとの動きではなく、1体ごとの動き。たとえば、画面外から編隊を組んで1体ずつ登場するなら、
> 静止するタイミングなどはそれぞれ異なるはず。フォーメーションをきっちり見せるのではなく、
> 1体ずつバラバラに動いているけど、登場位置やタイミングをずらすことで流れるように綺麗に見える。

これを受けて、仕様書にはこう書かれた。

> - 各機は自分の時計を持つ。開始が数フレームずつ遅れる(目安 8〜14フレーム)
> - **全機が同じ場所から出て同じ道を通る。違うのは開始時刻と停止位置だけ**
> - 停止位置は進行方向に沿ってずらす → 流れた結果として斜線に並ぶ

## 何が起きたか

実装した。実測もした。数字はこう出た。

```
個体0 開始t=1   停止(74,64) 静止中の移動量=0
個体1 開始t=-10 停止(64,50) 静止中の移動量=0
個体2 開始t=-21 停止(54,36) 静止中の移動量=0
個体3 開始t=-32 停止(44,22) 静止中の移動量=0
```

開始は11フレームずつずれている。停止位置は斜線に並んでいる。静止中は完全に止まっている。
仕様に書かれた条件を全部満たしていたので、私は「できた」と報告した。

ユーザーの評価は**却下**だった。

> かなり変。登場するドリフターは、すべておなじになってる?

コードを読み直すと、原因はすぐ分かった。私はこう書いていた。

```js
e.anchorX = waveBaseX + (...) * memberIndex * DRIFTER_TARGET_X_STEP;
e.anchorY = DRIFTER_TARGET_Y - memberIndex * DRIFTER_TARGET_Y_STEP;
e.vx = ((e.anchorX - e.x) / DRIFTER_ENTRY_FRAMES) | 0;  // ← これ
e.vy = ((e.anchorY - e.y) / DRIFTER_ENTRY_FRAMES) | 0;  // ← これ
```

**停止座標を先に決めて、そこへ60フレームで着くように速度を逆算していた。**

停止位置が機ごとに違う以上、逆算される速度も機ごとに違う。実測すると先頭機は 1.33px/frame、
4機目は 0.63px/frame で、**倍以上の速度差**があった。横方向にも別々の向きへ散っていた。
同じ地点から扇状に、しかもバラバラの速さで広がっていたことになる。

「1体ずつバラバラに動いているが流れるように見える」の、ちょうど逆だった。
**本当にバラバラに見えていた。**

## なぜそうなったか

仕様の「**同じ道を通る**」が、実装から見て一意でなかった。

- 私の解釈: 同じ地点から出て同じ目的地の周辺へ向かう = 通る空間がだいたい同じ
- 意図された解釈: **同じ向き・同じ速さのベクトルを共有する** = 軌跡が文字どおり重なる

そして「**違うのは開始時刻と停止位置だけ**」という一文が、誤解を強化した。
停止位置が自由に決められるパラメータとして読めるからだ。停止位置を先に決めてよいなら、
そこへ到達する手段(速度)は逆算するのが最も素直な実装になる。

つまり仕様は、**変えてよいもの(停止位置)を挙げていたが、変えてはいけないもの(速度と向き)を
明示していなかった**。禁止事項が書かれていない以上、実装は「書かれた条件を満たす最も簡単な方法」を選ぶ。
それが逆算だった。

さらに悪いことに、**この誤りは検証をすり抜けた**。私が測った項目は
「開始が11フレームずつずれているか」「停止位置が斜線に並ぶか」「静止中に動いていないか」で、
全部が仕様の文言そのままだった。**速度が全機で同じかどうかは、仕様に書かれていないので測らなかった。**
仕様の曖昧さが、実装だけでなく検証項目にもそのまま伝染していた。

## どう直したか

仕様が「速度と進行方向は全機まったく同じにする。ここを違えてはいけない」と書き直され、
やってはいけない実装(停止座標からの逆算)が明示された。実装はそれに従って作り直した。

- 進入の向きと速さは**種ごとに1本の定数**。全機がそれを共有する
- 機ごとに違うのは「いつ出発するか」と「**何フレーム進んで止まるか**」だけ
- 停止位置は座標ではなく**進む距離(フレーム数)**で持つ。60 / 52 / 44 / 36 と短くしていく

停止位置は「決めるもの」から「進んだ結果」になった。これで扇状に散りようがない。

直したあとの実測はこうなった。

```
個体 | 進入中の(vx,vy) | travel | 停止位置
1機目 | (0, 341)      | 60     | (74, 63)
2機目 | (0, 341)      | 52     | (74, 53)
3機目 | (0, 341)      | 44     | (74, 42)
4機目 | (0, 341)      | 36     | (74, 31)
```

速度は完全に一致し、停止位置は同じ道の上に一列に並んだ。
斜めに入る左出現でも全機 (160, 341) で一致する。

### ついでに見つかったバグ

直す過程で、停止位置の**順序が逆**になっていることに気づいた。先頭機が最も深く入るはずが、
後続ほど深い位置で止まっていた。

原因は待機中の扱いだった。出発前(自分の時計が負の間)も共通の更新処理が毎フレーム vy を積んでいて、
**待っている間に降りていた**。待つ時間が長い後続ほど深い位置から進入を始めるので、順序が反転する。
出発前に vy を 0 にして解決した。

これは仕様の問題ではなく素直な実装漏れだが、**「同じ道を通る」を速度の共有として実装して初めて
見えた**バグでもある。座標を逆算していた頃は、待機中のドリフトも逆算に吸収されて見えなかった。

## また踏んだ罠

修正後の計測で、個体3だけ進入中の速度が2種類記録され、静止中の移動量が26と出た。
一瞬「まだ直っていない」と思ったが、原因は計測側だった。
**プールのスロット番号だけをキーにして集計していた**ので、そのスロットが別のウェーブの個体に
再利用され、2体分の記録が1つに混ざっていた。

これは devlog 004 に自分で書いた罠そのものだ。世代付きキー(`formationId:slot`)で測り直したら、
数字はきれいに揃った。**書いた本人が、同じ形の計測を書き直すときに再び踏んだ**。
教訓を文章にしても、次に手を動かすときに思い出せるとは限らない。
プローブの雛形自体を世代付きキーで書いておくべきだった。

## 一般化できること

- **仕様には「変えてよいもの」だけでなく「変えてはいけないもの」を書く。**
  自由に決めてよいパラメータを列挙すると、実装はそれを起点に逆算する。
  逆算されると困る量があるなら、それを不変量として名指しする必要がある
- **曖昧な仕様は、検証項目まで曖昧にする。** 実装者は仕様の文言をそのまま検査項目に写すので、
  仕様に書かれていない不変量は測られない。**バグは実装ではなく、測っていない場所に残る**
- **「条件を全部満たしているのに間違っている」ときは、条件の書き方を疑う。**
  実装を責めても直らない。実際、書き直しは仕様の一文が変わってから10分で終わった
- **座標を先に決めるか、速度を先に決めるかは設計判断である。**
  見た目が「揃って流れる」ことを求めるなら速度を固定して結果として位置が決まる形にする。
  位置を固定すると速度が暴れる。どちらを不変量にするかで、絵が決まる
